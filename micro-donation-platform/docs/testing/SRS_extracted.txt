1. Introduction
1. Introduction
1.1 Purpose
This SRS defines the functional and non-functional requirements for a Micro Donation
Platform — a web application that lets users donate small amounts (₹1–₹500) to verified
causes and individuals.

1.2 Scope
The platform covers donor registration, cause discovery, payment processing, campaign
management, and impact reporting. Out of scope: physical fundraising, non-digital
payments, and regulatory compliance beyond India (UPI/Razorpay).

1.3 Document Conventions
FR-xx: Functional Requirement
NFR-xx: Non-Functional Requirement
UC-xx: Use Case
Priority levels: P1 (must-have), P2 (should-have), P3 (nice-to-have)

1.4 Intended Audience
Developers, testers, and the SE course evaluator. Assumes basic familiarity with web
applications.

2. Overall Description
2. Overall Description
2.1 Product Perspective
A standalone web platform (React + Node.js) integrated with UPI/Razorpay for payments
and a PostgreSQL backend. Runs on the public internet; no hardware dependencies.

2.2 Product Features (Summary)
Donor account creation and authentication
Campaign creation by verified cause owners
Micro-donation processing (₹1–₹500 per transaction)
Real-time donation tracker and impact dashboard
Admin panel for campaign verification and moderation

5. System Architecture Overview
5. System Architecture Overview
3-tier architecture: React SPA → REST API (Node.js/Express) → PostgreSQL. Razorpay
handles all payment flows externally.

Key API modules: /auth , /campaigns , /donations , /admin , /users
All frontend-to-backend calls use JWT bearer tokens. Razorpay webhooks are verified via
HMAC signature before updating donation status.

UC-01: Donor Makes a Micro Donation

1. Donor browses campaigns and selects one.

2. Donor clicks Donate, enters amount (₹1–₹500).
3. System opens Razorpay checkout.
4. Donor completes payment.
5. System confirms payment via webhook, updates progress bar, emails receipt.
Alternate: Payment fails → system shows error, donation not recorded.

UC-02: Campaign Owner Creates a Campaign
Actor: Campaign Owner Precondition: Owner account is verified.
1. Owner navigates to Create Campaign.
2. Fills in title, story, goal, category, deadline.
3. Uploads supporting documents.
4. Submits — status set to Pending Review.
5. Admin reviews and approves/rejects.
6. On approval, campaign goes live.

UC-03: Admin Moderates a Campaign
Actor: Admin Precondition: At least one campaign in Pending Review.
1. Admin opens the moderation queue.
2. Reviews details and documents.
3. Approves (campaign goes live) or Rejects (owner notified with reason).

UC-04: Donor Views Impact Dashboard
Actor: Donor Precondition: Donor has at least one completed donation.
1. Donor navigates to My Impact.
2. System shows total donated, number of campaigns supported, and categories
breakdown.

7. Constraints & Assumptions
7. Constraints & Assumptions
Technical Constraints
Payment gateway limited to Razorpay (India); international cards are a stretch goal.
Max donation per transaction: ₹500 (platform policy, not a technical limit).
File uploads (campaign images) capped at 5 MB per file.
Business Constraints
Platform takes 0% cut in the MVP; payment gateway fees (~2%) apply.
Campaigns must be manually approved by admin before going live.
Assumptions
All users have internet access and a UPI-linked device or card.
Team uses Razorpay test mode throughout development; live keys added before demo.
The platform is a course project — no real money will be processed.
